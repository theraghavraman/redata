# Benchmark results

Generated by `python benchmarks/summarize_results.py` from the JSON files in [results/](results/). Do not edit by hand.

Every row is one recorded run on one machine. The numbers describe that machine and that data, not what ReData will do everywhere. Each result file records the commit, the software versions, the dataset checksum and the correctness checks that had to pass for the run to count.

## Sync pipeline

`run_sync_benchmark.py`: a 6-column table synced from a local SQLite file into DuckDB staging tables through the real pipeline. There is no network in this measurement, so for remote databases read the rows/second as an upper bound. Every run checks row counts and `sum(amount)` against the source, that append read only the new rows, and that upsert left one row per key.

"SQL aggregate" is the median of repeated `SELECT COUNT(*), SUM(value)` requests. Every run checks the row count, the column count and the sum against independently computed values.

## What these results do not show

- They are not a reproduction of the older timings quoted from the v0.1.0 README (a 1 crore row, 723 MB file on a 2-core machine). That input and machine are not available.
- Runs marked "single run" have no repeat, so they carry no estimate of run-to-run variation.
- Browser-only mode is not measured here.
- No remote database, S3 or REST source is measured.
